# ADR-0000: 애플리케이션 레포와 인프라 레포를 분리한다

- **상태**: Accepted
- **날짜**: 2026-08-11
- **작성자**: (작성자 이름)
- **관련 ADR**: ADR-0001(배포 플랫폼), ADR-0002(런타임 베이스 이미지)

---

## 맥락 (Context)

Go로 작성된 백엔드 API(`api-server`)를 운영 가능한 상태로 만들어야 한다. 현재 상태는 다음과 같다.

- 애플리케이션 코드는 `api-server` 레포에 있고 개발팀이 관리한다
- 인프라, CI/CD, 운영 문서는 아직 존재하지 않는다
- 인프라 작업을 시작하려면 코드가 어디에 놓일지부터 정해야 한다
- 인프라 코드는 VPC, IAM, RDS를 생성하는 강한 AWS 권한을 필요로 한다
- 앱 코드 변경 주기와 인프라 변경 주기가 다르다

이 결정은 이후 CI/CD 파이프라인 구조, 배포 트리거, 롤백 절차를 전부 좌우하므로 다른 어떤 결정보다 먼저 확정한다.

## 결정 (Decision)

애플리케이션 코드는 `api-server` 레포에, 인프라 코드·CI/CD 정의·운영 문서·의사결정 기록은 `devops-project` 레포에 둔다.

배포 대상 이미지 태그는 `devops-project`에 명시적으로 기록하며, **이 값의 변경이 곧 배포 행위**로 정의한다.

## 고려한 선택지 (Options Considered)

### 선택지 A: 모노레포 (앱 + 인프라를 `api-server` 하나에)

- 장점
  - 앱 변경과 인프라 변경이 하나의 PR, 하나의 커밋으로 묶인다. "이 커밋이 곧 운영 상태"가 자명하다
  - 크로스 레포 트리거가 필요 없어 CI/CD가 단순하다
  - 롤백이 단순하다 — 커밋 하나를 되돌리면 앱과 인프라가 함께 되돌아간다
- 단점
  - CI에 부여하는 AWS 권한이 하나로 합쳐진다. 앱 코드에만 관여하는 사람도 인프라를 바꿀 수 있는 경로가 열린다
  - 앱 코드 변경마다 인프라 파이프라인이 트리거되지 않도록 경로 필터를 세밀하게 관리해야 한다
  - 앱 레포는 개발팀 소유라 DevOps가 레포 정책(브랜치 보호, 워크플로)을 자유롭게 바꾸기 어렵다
- 예상 비용: 추가 비용 없음
- 기각 이유: **권한 분리가 불가능하다는 점**이 결정적이었다. 실제 조직에서 앱 개발자와 인프라 담당자의 AWS 권한 범위는 달라야 하는데, 모노레포에서는 CI 자격증명을 하나로 쓰게 되어 최소 권한 원칙을 지키기 어렵다.

### 선택지 B: 레포 분리 (채택)

- 장점
  - 권한을 분리할 수 있다. `api-server`의 CI에는 ECR push 권한만, `devops-project`에는 인프라 생성 권한을 부여한다
  - 배포 이력이 `devops-project`의 커밋 히스토리로 남는다. "지금 운영에 어떤 버전이 떠 있는가"를 git log로 답할 수 있다
  - 인프라만 변경할 때 앱 파이프라인이 돌지 않는다
  - 앱 레포 소유권이 개발팀에 있어도 인프라 레포의 정책은 독립적으로 통제할 수 있다
- 단점
  - 앱 CI가 인프라 레포를 갱신해야 하므로 크로스 레포 인증 수단이 필요하다. 기본 `GITHUB_TOKEN`은 다른 레포에 쓸 수 없다
  - "배포된 상태"가 두 레포에 걸쳐 있어, 이미지 태그 기록 방식을 잘못 정하면 추적이 어려워진다
  - 롤백 시 앱 커밋과 인프라 커밋 중 무엇을 되돌리는지 명시적으로 정의해야 한다
- 예상 비용: 추가 비용 없음 (GitHub App 사용 시에도 무료)
- 채택 이유: 단점 세 가지가 모두 **설계로 해결 가능한 문제**인 반면, 선택지 A의 권한 문제는 구조적으로 해결이 어렵다. 또한 이 프로젝트의 목적이 실제 운영 조직의 구조를 경험하는 것이므로, 권한 경계가 존재하는 형태가 학습 목적에도 부합한다.

### 선택지 C: 하이브리드 (인프라 모듈은 별도 레포, 배포 매니페스트는 앱 레포에)

- 장점
  - 재사용 가능한 Terraform 모듈을 여러 서비스가 공유할 수 있다
  - 배포 대상 버전은 앱 레포에 있어 개발자가 자기 서비스 배포를 직접 통제한다
- 단점
  - 레포가 사실상 3종(앱, 모듈, 환경 정의)으로 늘어나 지금 규모에 과하다
  - 서비스가 하나뿐인 현 시점에 모듈 재사용 이점이 없다
- 예상 비용: 관리 대상 레포 증가에 따른 운영 부담
- 기각 이유: 서비스가 1개인 상태에서 얻는 이득이 없다. 서비스가 여러 개로 늘어나면 이 형태를 재검토한다.

## 결과 (Consequences)

### 좋아지는 것

- CI/CD 자격증명을 레포별로 최소 권한으로 분리할 수 있다
- 인프라 변경 이력과 배포 이력이 한 레포에 모여 감사(audit)가 쉬워진다
- 앱 개발 속도와 인프라 변경이 서로를 막지 않는다

### 나빠지는 것 / 감수하는 비용

- **크로스 레포 트리거가 필요하다.** 앱 CI가 이미지를 ECR에 올린 뒤 `devops-project`의 태그를 갱신해야 한다. GitHub App 또는 PAT 발급·보관·로테이션이 추가 업무로 생긴다
- **배포 상태가 두 레포에 걸친다.** 이미지 태그의 기록 위치와 형식을 엄격히 정하지 않으면 "무엇이 떠 있는지 모르는" 상태가 될 수 있다
- **롤백 절차가 한 단계 복잡해진다.** 앱 코드를 되돌릴 것인지 배포 태그를 되돌릴 것인지 구분해야 한다
- 신규 합류자가 두 레포를 모두 이해해야 하므로 온보딩 문서 부담이 늘어난다

### 이 결정 때문에 뒤따라야 하는 후속 작업

- [ ] 배포 대상 이미지 태그의 **기록 위치와 형식**을 정한다 (`devops-project` 내 단일 파일)
- [ ] 이미지 태그를 immutable하게 만든다 (커밋 SHA 기반). mutable 태그를 쓰면 위 기록이 무의미해진다 → ADR-0002 / Phase 1
- [ ] 크로스 레포 인증 방식을 결정한다 (GitHub App vs PAT) → Phase 3
- [ ] 레포별 AWS IAM 역할을 분리 설계한다 (OIDC 신뢰 정책의 `sub` 조건으로 레포를 제한) → Phase 2
- [ ] 롤백 절차를 Runbook에 명문화한다 → Phase 6

## 재검토 트리거 (Revisit When)

- 관리하는 서비스가 3개를 넘어가면 → 선택지 C(모듈 분리)를 재검토
- 크로스 레포 트리거 장애가 반복적으로 배포를 막으면 → 선택지 A(모노레포) 재검토
- 앱 레포와 인프라 레포의 소유 팀이 동일해지면 → 분리의 근거였던 권한 분리 이점이 약해지므로 재검토
