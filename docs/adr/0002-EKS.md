# ADR-0002: 컨테이너 오케스트레이션 — EKS

- **상태**: Accepted
- **날짜**: 2026-08-21
- **관련 Phase**: Phase 2
- **영향받는 후속 Phase**:  Phase 3 (CD의 배포 방식이 EKS 전제),
  Phase 4 (워크로드 배포·Ingress가 EKS 위에서 진행),
  Phase 9 (노드 오토스케일링 도구 선정이 EKS 전제)

## Context

이 결정은 멘토가 지정했다(2026-08-17 멘토 피드백, [메모](../notes/2026-08-17-phase2-mentor-notes.md)).
본 문서는 그 결정의 근거를 스스로 재구성해 기록한 것이다.

프로젝트의 목표는 동작하는 인프라 자체가 아니라 **운영 가능한 인프라를
직접 설계·구축하는 경험(학습)**이다. 오케스트레이션 계층이 확정되어야
Phase 2의 네트워크·IAM 설계와 Terraform 구현 범위가 정해진다.

## 결정 (Decision)

**EKS (EC2 노드)를 사용한다.**

## 고려한 선택지 (Options Considered)

| 항목 | ECS (EC2/Fargate) | **EKS (EC2 노드) — 선택** | EKS on Fargate |
|---|---|---|---|
| 오케스트레이터 | AWS 자체 | Kubernetes | Kubernetes |
| 컨트롤 플레인 비용 | 무료 | 시간당 과금 ($0.10/hr) | 시간당 과금 (동일) |
| 학습 곡선 | 낮음 | **높음 — 이 프로젝트에서는 비용이 아니라 목적이다** | 중간 |
| 이식성·생태계 | AWS 종속 | K8s 생태계 전체 (Helm, ArgoCD 등) | 제한적 — DaemonSet·HostNetwork/HostPort 불가, GPU 미지원 |
| 노드 관리 | 선택 — Fargate 사용 시 없음 | 직접 관리 — [network-architecture.md](../design/network-architecture.md) §4~5에서 노드 배치·서브넷을 설계한 이유 | 없음 — Pod 단위 과금 |
| 채용 시장 신호 | 보통 | 높음 | 해당 없음 |

## 결과 (Consequences)

EKS (EC2 노드)를 선택했다. 컨트롤 플레인 비용과 학습 곡선은 다른 두
선택지보다 불리하지만, 이 프로젝트의 목표가 "운영 가능한 인프라를 직접
설계·구축하는 경험"이므로 노드 관리를 대체하는 선택지(Fargate)는 학습
대상을 제거해버린다. ECS는 학습 비용이 가장 낮은 대신 K8s 생태계와 채용
시장 신호를 얻지 못한다.

## 재검토 트리거
학습이 끝나고 이 인프라를 상시 운영하며 비용 최소화가 우선이 되는 시점, 해당 EKS 서비스를 지속할 것인지에대한 여부
