# 멘토 피드백 정리 (2026-08-17) — Phase 1 보완 + Phase 2 방향

원본: 구두 피드백 메모. 이 문서는 내용을 주제별로 재구성한 것.

## 1. 문서 작성 피드백

- ADR은 지금 분량 또는 **더 짧아도 된다.** 중요한 것은 양이 아니라
  "왜 그렇게 했고, 어디에 포인트를 두었는지"의 설명력
- 쓰다 보면 늘고, 많이 이야기할수록 더 잘하게 된다

## 2. Phase 1 보완 과제 — Makefile 퀵런치

- runbook은 길다. 오픈소스/외부 개발자 관점에서는 명령 1~2개가 이상적
- **`make init` / `make run`** 으로 설치·의존성·compose 기동까지 한 번에
- runbook을 대체하는 게 아니라, 진입 경로를 짧게 만드는 것
  (runbook = 상세·문제해결, Makefile = 퀵스타트)

## 3. Phase 2 확정 사항 (기존 계획에서 변경)

| 항목 | 기존 계획 | 변경 |
|---|---|---|
| 오케스트레이션 | ECS vs EKS를 Phase 2~4에서 결정 | **EKS로 확정** (학습 목적) |
| DB | RDS를 Phase 2에서 구성 | **DB 제외.** EKS만 구성 |
| 인프라 코드 위치 | (미정) | **Terraform 전용 인프라 레포 신설** |
| 용량 가정 | 없음 | **초당 10 요청** 규모로 설계 |
| 노드 | — | 3개, AZ 분산(HA) 고민 포함 |

## 4. EKS 학습 주제 (멘토 언급 키워드 정리)

- **컨트롤 플레인은 매니지드** — 직접 구성할 필요 없음. EKS의 특성 이해
- **노드 배치와 HA**: 어느 zone에 노드를 둘 것인가,
  taints & tolerations, pod anti-affinity
- **노드 접근**: 노드에 SSH로 직접 들어가지 않는다 — 같은 네트워크의
  CloudShell 또는 SSM 에이전트 경유
- **kubectl** 핸들링(기본 커맨드)
- **노드 오토스케일링**: Karpenter(오픈소스) vs EKS Cluster Autoscaler
- 구성 순서: AWS 인프라 레벨(VPC 등) → EKS 클러스터 → 클러스터 내부

## 5. 네트워크 설계 원칙

- **서브넷은 타이트하게 조인다.** /24 남발은 IP 낭비
- 실제 워크로드는 프라이빗에 많고, 퍼블릭은 좁게 (/26~/28 수준)
- 사이트 간 VPN 연결 시 IP 대역 충돌 문제 때문에 VPC CIDR은 넉넉히,
  서브넷은 필요 시 VPC 안에서 얼마든지 추가할 수 있으니 용도별로 계산해서
- 퍼블릭 서브넷 + 프라이빗 서브넷 구조, DB 없음

## 6. 멀티 어카운트 (엔터프라이즈 표준)

- 실제 프로덕션에서는 **네트워크(서브넷 등)를 만드는 어카운트와
  EKS를 구성하는 어카운트를 분리**한다
- 이유: 담당 조직이 다르다 — 네트워크는 보안/인프라 조직,
  EKS 배포·관리는 DevOps/개발팀
- 어카운트 단위로 경계를 쪼개는 것이 엔터프라이즈 표준

## 7. IAM 원칙

- **IAM User를 만들지 않는다. 전부 Role + AssumeRole**
- 최소 권한 원칙 — admin 금지
- EKS 내부 워크로드 권한: **IRSA** (IAM Roles for Service Accounts)
- EKS 외부: Organizations / OU / IAM Role 구조로
- 도메인 구매 후 권한별 테스트 계정 구성

## 8. 과제 (멘토 지정)

1. **엔터프라이즈 가정 시 AWS Organizations / OU 구조 설계** —
   정식 프로덕션 버전 (설계 문서)
2. **단순화해서 실제 적용할 네트워크 구조 설계** — 1번을 1인 프로젝트
   규모로 축소한 실작업 버전
3. **아키텍처 다이어그램 작성** — VPC, 퍼블릭/프라이빗 서브넷, EKS,
   IAM Role 포함. Terraform 작성 전에 그린다
4. Phase 1 보완: Makefile 퀵런치 (`make init` / `make run`)
